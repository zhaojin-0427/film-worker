# 服务端返修增量接入

返修增量包只传 `feedback_manifest` 标出的帧。比如全片 130 帧，打回 5 帧，同机审片只传 5 张对比 JPG 和索引。集中存储还传这 5 帧的无损白模 PNG。首制、成片和其他工件的传输沿用现有协议。

## 注册与发放

执行端随注册发送 `X-Film-Worker-Review-Upload: rejected_frames_v1`。247 为支持该能力的节点发放新返修工单时，可在 `input_manifest` 写入 `"review_upload": "rejected_frames_v1"`，并重新计算 `input_manifest_sha256`。续租和重试沿用冻结的清单。旧协议省略该字段。基版已经使用增量协议时，后续返修和出片也要派给声明该能力的节点。

## 接收与合并

1. `review_bundle` 仍是 ZIP。`index.json` 和 `version_manifest` 都携带相同的 `review_delta`，其中包含 `mode`、`base_version`、`base_manifest_sha256`、`frames` 和 `full_files_sha256`。两份清单的常规 `frames` 字段保留全片帧号、PTS、路径和签名。`review_bundle_sha256` 对应实际收到的增量 ZIP 字节。
2. 核对返修工单的模式、基版版本号和原始版本清单摘要。验证 `review_delta.frames` 与意见清单的帧号集合完全一致，且为唯一、升序的帧号。用现有索引和媒体规则验证每个上传文件。`files` 及实际 ZIP 条目必须精确覆盖这些帧对应的 JPG，以及集中存储下对应的 PNG。
3. 从已核验的完整基版继承未打回帧的图片及文件条目。这些帧的 `frames` 记录须与基版一致。合并后的 `files` 数组按 `path` 排序，使用 RFC 8785 规范化 JSON 计算 SHA-256，结果必须等于 `review_delta.full_files_sha256`。全部通过后原子提交新版，沿用逐帧复审规则。
4. 保留执行端提交的原始 `version_manifest` 字节。集中存储的后续工单通过 `review_bundle` 提供合并后的全帧 ZIP，并在下载工件清单填该 ZIP 自己的 SHA-256。全帧 ZIP 内 `index.json` 省略 `review_delta`，完整列出 `files`，其余字段使用新版索引。执行端用冻结的 `full_files_sha256` 检查其内容。同机模式下，执行端自行保留该全帧 ZIP 及无损白模帧。

联调时用有打回帧和未审帧的作业，验证增量工件字节、继承图片、逐帧复审及第二次返修或出片。 [OpenAPI 定义](../contract.openapi.yaml)
